| 文件 | 内容 |

| `.gitignore` | 忽略日志、临时文件、`node_modules` |

---

## 2. 脚本

```json
"scripts": {
  "start":   "electron .",
  "rebuild": "electron-rebuild -f -w better-sqlite3",
  "check":   "node --check main.js && node --check database.js && node --check preload.js && node --check renderer.js && node --check story-editor.js && node --check markdown.js && node --check theme-init.js"
}
```

| 脚本 | 用途 | 何时用 |
| --- | --- | --- |
| `npm start` | 以 Electron 加载项目根目录 | 日常启动；`electron .` 读 `package.json` 的 `main: main.js` |
| `npm run rebuild` | 用 `@electron/rebuild` 为 Electron ABI 重编 better-sqlite3 | 报 `NODE_MODULE_VERSION` 不匹配时 |
| `npm run check` | 逐个文件 `node --check` 做语法检查 | 每次改完 JS，替代「启动才发现语法错」 |

`check` 的局限：只做语法解析，**不检查未定义变量、拼写错误、逻辑问题**；且不包含 HTML/CSS。
新增 JS 文件时必须把文件名加进这条命令。

## 4. 原生模块 ABI 对照

Electron 的 Node ABI 与系统 Node 不同，`better_sqlite3.node` 必须按 Electron 版本编译：

| Electron | NODE_MODULE_VERSION | 预编译包后缀 |
| --- | --- | --- |
| 33.x | **130** | `electron-v130-win32-x64` |
| 32.x | 128 | `electron-v128-win32-x64` |
| 31.x | 125 | `electron-v125-win32-x64` |

判断当前二进制是否匹配：

```bash
ELECTRON_RUN_AS_NODE=1 node_modules/electron/dist/electron.exe -e \
  "const D=require('better-sqlite3'); const d=new D('data/characters.db',{readonly:true});
   console.log('OK', d.prepare('select count(*) c from characters').get());"
```

- 成功 → ABI 正确；
- `Could not locate the bindings file` → `.node` 文件丢失；
- `NODE_MODULE_VERSION 130 vs 127` → ABI 不匹配。

**不要用系统 Node 直接 `require('better-sqlite3')` 判断**：即使二进制正常，系统 Node（v22 的 ABI 127）
也加载不了为 Electron 编译的版本，会误判成「坏了」。

## 5. 原生模块恢复（无 VS 编译环境）

`npm run rebuild` 需要 Visual Studio 的「使用 C++ 的桌面开发」工作负载，
未安装时必然失败。此时直接取官方预编译包：

```bash
# GitHub 通常不可达，用 npmmirror
curl -L -o bs3.tar.gz \
  "https://registry.npmmirror.com/-/binary/better-sqlite3/v11.10.0/better-sqlite3-v11.10.0-electron-v130-win32-x64.tar.gz"

tar -xzf bs3.tar.gz -C node_modules/better-sqlite3
# 解包后得到 node_modules/better-sqlite3/build/Release/better_sqlite3.node
```

包内容就是 `build/Release/`，解包路径必须指向 `node_modules/better-sqlite3`。

验证：

```bash
ls -l node_modules/better-sqlite3/build/Release/better_sqlite3.node   # 约 1.7 MB
npm start
```

## 6. 打包分发（尚未配置）

`package.json` 里**没有 `build` 字段，也没装 `electron-builder`**，目前只能源码运行。
若要分发 exe，建议：

1. `npm i -D electron-builder`；
2. 加 `build` 配置（`appId` / `productName` / `win.target: nsis` / `files` 白名单）；
3. 关键注意：`better-sqlite3` 是原生依赖，需要 `asarUnpack` 或在打包后对其重建 ABI；
4. `data/` 与 `images/` 属于用户数据，**不应打进安装包**，应在首次启动时由 `ensureDirs()` 创建。

## 7. 仓库卫生

**远端仓库**：`https://github.com/death1001/oc--`（public），默认分支 `main`。
> 该仓库于 **2026-10-29 删除并重建过一次**，目的是彻底抹掉早期提交里的个人数据，详见 §7.4。

### 7.1 什么进 Git，什么不进

| 进 | 不进（本机私有） |
| --- | --- |
| 全部源码、`package.json` / `package-lock.json`、`README.md`、`docs/` | `data/`：SQLite 数据库，即用户的全部角色 / 故事 / 关系 |
| `.gitignore` 自身 | `images/`：上传的立绘与头像原图 |
| | `.workbuddy/`：项目笔记与协作记录 |
| | `.tmp_prebuild/`、`node_modules/`、`*.log`、`*.pid` |

判断标准只有一条：**能从这个仓库重建出一个能跑的程序 = 该进；属于"某个人写的内容" = 不该进。**

### 7.2 `.gitignore` 全文

```
data/            # 角色数据库（个人创作）
images/          # 立绘与头像（个人素材）
.workbuddy/      # 本机工作记录
node_modules/
.tmp_prebuild/
*.log  *.pid  *.tmp  *~
.DS_Store  Thumbs.db  desktop.ini
.vscode/  .idea/
```

### 7.3 新机器 clone 下来能直接跑

`database.js` 的 `ensureDirs()` 在 `initDatabase()` 里执行，会 `mkdir -p` 出
`data/` 与 `images/`，并建好空表。所以**缺少这两个目录不是故障**，首次启动会自动生成空库。
反过来，如果你把本机的 `data/characters.db` 拷到别的机器，就是在迁移数据 —— 这属于备份动作，
不要通过 Git 做。

### 7.4 曾经踩过的坑：个人数据进过历史（2026-10-29 已处理）

首次提交（`1c3a076`，2026-08-22）时没有 `.gitignore` 规则，`data/characters.db` 与 4 张立绘
被一起提交并推到了这个 **public** 仓库。之后只是"停止跟踪"是不够的 —— 旧提交里仍然翻得到。

处理方式（完整重写历史）：

```bash
# 1) 加 .gitignore，并把已跟踪的个人数据从索引移除（工作区文件保留）
git rm -r --cached data images

# 2) 重写所有提交，逐个把这两个路径擦掉
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch --force \
  --index-filter 'git rm -r --cached --ignore-unmatch -q data images' \
  --prune-empty -- --all

# 3) 带租约强推（比 --force 安全：远端若被别人改过会拒绝）
git push --force-with-lease=main:<旧 HEAD> origin main

# 4) 清掉本地残留：refs/original、reflog、旧对象
git update-ref -d refs/original/refs/heads/main
git reflog expire --expire=now --all && git gc --prune=now
```

**注意事项**

- `--force-with-lease=<ref>:<旧 SHA>` 要显式给旧值：`filter-branch` 会连
  `refs/remotes/origin/main` 一起改写，此时裸的 `--force-with-lease` 拿不到正确的期望值会直接失败。
- 重写后**旧提交仍在 GitHub 上**能按 SHA 直接访问（`api.github.com/repos/.../commits/<旧SHA>` 仍返回 200），
  这是服务端的悬空对象，只能等它 GC、联系 GitHub Support 请求清除，或者删库重建。
  换言之：强推能挡住"翻历史"，挡不住"拿着 SHA 直接看"。

#### 最终处理：删库重建（2026-10-29 晚）

因为强推清不掉悬空对象，最终走了彻底路线：

| 步骤 | 做法 |
| --- | --- |
| 删库 | 网页 Settings → Danger Zone → Delete this repository（API 删除需要 `delete_repo` 权限，本机 GCM 的 token 只有 `repo`，`DELETE /repos/...` 返回 403 `Must have admin rights`） |
| 重建 | `POST /user/repos`，`{"name":"oc--","private":false}` —— 创建只需要 `repo` 权限 |
| 重推 | `git push -u origin main`，4 个提交一起上（提交对象都在本地，没丢） |

验证结果：

| 检查 | 结果 |
| --- | --- |
| 旧提交 `1c3a076…` | `422 No commit found for SHA`（重建前是 200） |
| 旧 blob `1d66238…`（characters.db） | `404` |
| 新 `main` | `200`，38 个文件 |
| 匿名访问 | `200`，`visibility: public` |

**结论**：`--force-with-lease` 只是解绑引用，对象还在；要真正抹掉痕迹，只有删库重建这一条路
（或者一开始就别把敏感文件提交进去）。
- 想彻底避免这件事，唯一可靠的做法是**第一次提交前**就把 `.gitignore` 写好。

### 7.5 根目录的调试残留

`app.pid` / `app-out.log` / `app-err.log` 是早期调试留下的（代码中无引用），已被 `.gitignore` 覆盖，可随时删除。

## 8. 修改指引

| 需求 | 做法 |
| --- | --- |
| 新增 JS 文件 | 加进 `check` 脚本，否则语法错误只能靠启动发现 |

| 接入打包 | 见第 6 节 |
